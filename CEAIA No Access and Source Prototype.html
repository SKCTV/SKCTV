Decisions — each question in the brief, answered

The prototype in views 2 and 3 implements all of these. Nothing below is a future intention.

D1 · How is a source marked in the reply — and with which brackets?

Numbered citations are not a standardised pattern in Bee, so what replaces 1 / 2 / 3? Parentheses, square brackets, or something else?

A Bee Icon Link in square brackets: [icon + short title]. The icon shows the source kind and the short title names the source, so the link is self-describing — no bare number, no legend to learn. Square brackets, not parentheses: parentheses read as an aside that belongs to the sentence (“the calendar (final v3)”), while square brackets are the established mark for an inserted citation and stay visibly separate from the prose. The full title appears in the hover preview, the end-of-reply list and the panel; the inline label is shortened to a few words. Colour is not used to carry any of this.

D2 · Telling web, upload and knowledge base apart

Differentiating web links from user uploads and knowledge-base material.

Icon in the link + Bee Tag naming the category, everywhere, without exception — and no colour coding. Bee has one simple Tag (a small grey label; the only other variant is the dark-blue Promotional Tag, which is not for this). So: Web link (globe icon + grey “Web link” tag), Your upload (upload arrow + “Your upload” tag), Knowledge base (book + “Knowledge base” tag). The word is always present, so the distinction survives greyscale, small sizes and screen readers. Behaviour reinforces it: web opens out, the other two open in the viewer.

D3 · Several sources for one part of a reply

What if a portion of the reply has multiple sources?

Place the bracketed links together — e.g. [Q3 change calendar] [Change policy] — and open the panel in “For this claim” mode, listing exactly those sources with the quoted chunk for each. No separate popover per source; the claim is the unit the user is checking.

D4 · Long names and long URLs

Show the full URL or full document name?

Never in full in the reply. The inline bracketed label is shortened to a few words with an ellipsis where needed; titles truncate with an ellipsis in source links and lists; the full title is on hover/focus and always in the panel and viewer header. URLs are never printed: show the source system and title (e.g. “Confluence · CAB approval checklist”), with the host or domain only in the viewer metadata. A full URL in body text is unreadable and unactionable.

D5 · Only at the end, or inside the reply too?

Referred material at the end of the reply, inline, or both?

Both, linked. Inline bracketed links mark where a claim comes from; the end-of-reply list shows everything the reply used. Clicking either lands on the same source in the same panel, so the two views never disagree.

D6 · “Sources” action, or show a few?

Only a Sources action, or the full / partial list with View more?

Show the first 3 source links plus a count and “View all”. Each is a Bee Icon Link with its Bee Tag, so three links prove at a glance that sources exist and what kinds they are; beyond three, links crowd the answer. “View all” opens the full panel list. A bare “Sources” button hides that information and costs an extra click to learn anything.

D7 · Clicking a source in the reply

Web vs. document behaviour.

Web links open in a new tab (they live outside CEAIA). Uploads and knowledge-base documents open in the embedded viewer in the right panel, scrolled to the cited chunk, with the chunk highlighted. The reply stays visible beside it.

D8 · Right panel or overlay modal?

How to view several sources for one claim.

Right panel. Checking a source means comparing it with the claim — the claim must stay on screen. A modal hides exactly what is being checked. The modal pattern is kept only as the small-screen fallback, where there is no room for side-by-side.

D9 · The source list itself

Full list design, in the right panel.

Grouped by type with counts, filterable and searchable. Groups: Web links, Your uploads, Knowledge base. Each row: type icon, full title (wraps to two lines), system and date, chunk count. Filters and search narrow the list without leaving it.

D10 · List → one item → back

Clicking an item in the full list — what does it look like?

The panel switches to viewer mode for that item, with “← All sources” at the top, the full title, type badge and metadata, then the document preview. Back returns to the same list position and filter. The chat never moves.

D11 · The viewer, all file types, all sizes

Embedded viewer for image, docs and PDFs; responsive; drag the divider; expand.

One viewer, five renderers: PDF pages, Word-style document, slide deck (PPTX, rendered as slides), image preview, and a web-link card. The divider drags (320–640 px, wider when expanded to 880 px); Expand takes the panel to near-full width; on small screens it becomes a sheet. Zoom controls are in the viewer header in production; this prototype shows page 1 with the cited chunk.

D12 · One experience, both agents

Consistent across normal and super agent, ahead of their merge.

Shared components, shared markers. Bracketed icon links, source lists, panel, viewer, Bee Tags and the chunk display are the same code and the same visuals in both modes. Only the shell differs (task plan / outputs in super agent). The parity table in view 3 is the checklist.

Edge cases the design must survive

No sources for a reply

No strip, no source links. A reply that used no retrievable source must not show an empty “Sources” section — that reads as a broken feature.

Source unavailable / broken URL

Directly from AIWPB-2816’s subtask (fix Confluence / Jira / attachment URLs): a source that cannot be resolved shows its title with an “Unavailable” state and the reason in the panel — never a dead link, never a silent omission.

Many sources (10+)

Inline bracketed links still group per claim; the end strip still shows 3 + count; the panel list groups, filters and searches. Nothing in the reply grows with the count.

Same source, several claims

One bracketed link per source, reused across claims. The panel shows every chunk from that source that was cited, grouped under the one title.

AIWPB-4988 — multiple upload

Uploading several files at once (My repository › Files) feeds the “Your upload” type. The composer in view 2 accepts multiple files and lists them as chips; each uploaded file becomes a citable source with its own chunks.

Chunk references (AIWPB-2816)

Every cited source shows the exact chunk text in the panel, highlighted in the viewer. “Knowledge content along with chunk references” is the requirement — a bare link to a whole document does not satisfy it.

CEAIA — No access (AIWPB-9195) and source reveal (AIWPB-2816, AIWPB-4988) · Prototype + analysis · 28 October 2026

1 · What was asked

  • AIWPB-9195 — CEAIA access denial. An authenticated HSBC employee without access who enters CEAIA (Prod or PrePROD) sees a clear, business-friendly denial only after successful authentication and failed authorisation; is told they do not have access; is directed to request access via a clickable link to the CEAIA space; sees the same message in both environments; is blocked from restricted functionality; has the event audit-logged without exposing authorisation logic; and the message and link are maintainable through configuration.
  • AIWPB-2816 — References in deep search results. Deep search / hybrid deep search results in both the normal agent and the super agent display the reference(s) alongside the answer or summary — knowledge content along with chunk references. Subtasks: fix the URL for Confluence, Jira or attachment; add citation logic to the prompt for the deep search part.
  • AIWPB-4988 — Multiple file upload. Upload multiple files at once in “My repository › Files”. In source terms, uploaded files are the “Your upload” source type; multi-upload is therefore part of the source story, not a separate feature.

2 · Sources consulted

  • CEAIA conceptual design in Figma — the “Generating replies” (super agent) frame and the “Initial chat” (normal agent) frame: shell header, functional header, welcome content, disclaimer note, right-hand Overview / Sources panel, composer. The header in this prototype reuses that design; the no-access body replaces the rest, as requested.
  • FigJam board “C4 — CEAIA”, section “Source function — references”: a collection of unlabelled screenshots from external AI products. The images were too small to attribute to individual products, so this report classifies patterns (view 4) rather than naming products. No pattern verdict depends on a single screenshot.
  • North Star asset library (node 1-7), “Illustrations (Work in Progress)” board: the denial page now carries an illustration redrawn in that board’s suggested empty-state direction — flat, muted panels on a soft ground shadow, as in WPBDR-1141 “Cards are not available” (the team’s suggested flat grey-blue card illustration, in preference to the colourful hand-and-magnifier draft; the literal card artwork was exported and inspected but is not embedded, because cards would wrongly suggest the page is about cards). The motif is redrawn, not copied literally: a locked panel replaces the cards, which would wrongly suggest the page is about cards rather than access. The message itself follows the conventions visible in the CEAIA frames (single clear heading, plain-language note box, one primary action).
  • FigJam ticket table (AIWPB-9195 / 2816 / 4988) as read on 28 October 2026, including the board comment record that multi-file upload was reported as still not working after five weeks, with platform enhancements planned for July 2026. That status is recorded here as a board record, not re-verified.

Bracketed Bee Icon Links inline with hover preview — [icon + short title] in square brackets, no numbered circles, which do not exist as a Bee pattern; full titles in the end-of-reply list (first 3 links + View all) and in the right panel; web / upload / knowledge-base distinguished by icon + plain grey Bee Tag everywhere, with no colour coding and no colourful tag; multi-source claims open the panel in claim mode with each chunk quoted; long titles shortened in the reply and full in the panel; web links open in a new tab, documents open in a resizable, expandable embedded viewer (PDF, Word, PPTX slides, image, web card); the full list groups by type with filter and search; list → viewer → back preserves place and filter; identical components in normal and super agent. 5 · Open questions & risks

  1. North Star message components: re-check the correct node for the intended message patterns (banner, inline, dialog) and confirm option A against the library before build. The illustration direction is now taken from the illustrations board (WPBDR-1141, adapted); the message-pattern check above is separate.
  2. URL fixing (AIWPB-2816 subtask): the prototype assumes resolved Confluence / Jira / attachment URLs exist at render time. Until that subtask lands, the “Unavailable” state (view 4) is the required fallback — never a dead link.
  3. Citation logic in the prompt: the UI assumes the model returns claim-to-chunk mappings. If the prompt work lands later than the UI, bracketed source links cannot be rendered honestly — show the end-of-reply list only, without inline links, in that interim state.
  4. 4988 delivery status: board comments record multi-upload as not working after five weeks. Confirm current status with the platform team before promising the composer behaviour in view 2.
  5. Access-request ownership: confirm who owns the CEAIA space page and the expected turnaround wording before launch; the prototype deliberately promises no timescale.
  6. Viewer scope: confirm which file types the embedded viewer must support at launch (PDF, DOCX, PPTX and images shown here; decks render as slides) and whether Office files render natively or via conversion.

6 · Handoff notes

  • One shared source-panel + viewer component serves both agent modes; do not build two.
  • Source type is data, not styling: every source record carries type (web / upload / knowledge-base), system (Confluence / Jira / upload), title, chunks[] and resolved URL or unavailable reason.
  • Accessibility: source links are real buttons labelled with the full source title and type; the panel is a complementary landmark; type is never colour alone (icon + Bee Tag word); the viewer works by keyboard (Tab to a source link, Enter to open, Back to return).

  1. North Star 消息组件：需对照正确节点复核预期的消息模式（横幅、行内、弹窗），并在开发前确认方案 A 是否符合组件库。插图方向现已取自插图白板（WPBDR-1141，改编后使用）；上述消息模式复核与之分开。
  2. URL 修复（AIWPB-2816 子任务）：原型假设渲染时 Confluence / Jira / 附件的 URL 已解析。在该子任务落地前，必须使用“不可用”状态（视图 4）作为兜底——绝不展示死链。
  3. 提示词中的引用逻辑：界面假设模型返回“主张—片段”映射关系。若提示词工作晚于界面上线，方括号来源链接无法真实渲染——过渡状态下仅展示回答末尾列表，不显示行内链接。
  4. 4988 交付状态：白板评论记录多文件上传在 5 周后仍未生效。承诺视图 2 中的输入框行为前，需与平台团队确认当前状态。
  5. 访问申请归属：上线前确认 CEAIA 空间页面的负责人与预期处理时长的措辞；原型有意不承诺任何时限。
  6. 查看器范围：确认上线时内嵌查看器必须支持的文件类型（此处展示 PDF、DOCX、PPTX 与图片；演示文稿按幻灯片渲染），以及 Office 文件是原生渲染还是经转换后渲染。

6 · 交接说明

  • 普通智能体与超级智能体共用同一个来源面板 + 查看器组件，不得分别构建两套。
  • 来源类型属于数据而非样式：每条来源记录需包含类型（网页 / 上传 / 知识库）、系统（Confluence / Jira / 上传）、标题、片段数组以及已解析 URL 或不可用原因。
  • 无障碍：来源链接为带有完整来源标题与类型标签的真实按钮；面板为辅助地标；类型绝不仅靠颜色区分（图标 + Bee 标签文字）；查看器支持键盘操作（Tab 定位来源链接，Enter 打开，返回键回到列表）。
